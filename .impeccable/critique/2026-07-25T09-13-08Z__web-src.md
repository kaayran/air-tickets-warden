## Design Specificity Verdict

**Category-generic telegram-ui scaffolding with a genuine coat of domain authorship in the copy — but zero authored visual or interaction identity.**

Strip the words and this is the reference telegram-ui gallery: `List → Section → Cell`, a `Tabbar`, a `Steps` wizard, a `Placeholder` empty state. A to-do app on this library would look identical. Authorship is real but lives only in language and data shaping: `formatRoute` → `BEG+1 → BCN, MAD`, the empty-state and `historical_minimum` copy, `subtitle` collapsing to "on price drop" when there's no threshold.

PRODUCT.md's core promise — "the craft shows in exactness and legibility," "instrument, not companion" — is not expressed visually. Prices, routes, and IATA codes are the product's nouns, yet they render in the default proportional body font (only the airport chips use `mono`). An instrument would set fares in tabular/monospaced numerics so a column of `€150 / €220 / €95` scans as a column. That one decision separates "a form app that happens to be about flights" from "a price instrument." Right now it's the former: the words were designed, the interface was assembled.

## Overall Impression

Honest, competent, and faithful to the product's voice — and visually anonymous. The single biggest opportunity is to make the interface *look and behave like an instrument*: authored typography for the product's numbers, a legible anti-spam Settings story, and a create path that respects the actual user (a friend flying a few known routes) instead of a stranger configuring everything from scratch. Two concrete correctness gaps (silent delete, displaced server errors) should be fixed regardless of the visual direction.

## What's Working

1. **Optimistic pause/mute with rollback** (SubscriptionsList.tsx:33–45): `onMutate` rewrites the cached row, `onError` restores `ctx.previous`, `onSettled` reconciles. Textbook, and exactly right for a phone where taps must feel instant.
2. **Browse-on-focus airport picker** (AirportPicker.tsx): empty-field focus shows major hubs, first-char search narrows, selections become removable `mono` chips, a 150ms blur delay stops a tap from dismissing the list mid-select. Every small decision respects the phone context.
3. **Copy that is the product**: "on price drop" subtitle, the `historical_minimum` footer, "the warden starts watching prices for you," the 401 recovery line. Dry, precise, emoji-free — Brand Commitments executed faithfully.

## Priority Issues

**[P1] Delete has no feedback and no error recovery** — `impeccable harden`
- *Why:* `deleteMutation` (SubscriptionsList.tsx:47–50) only invalidates `onSettled` — no optimistic removal, no loading, no `onError`. Destructive action + no feedback is the worst feedback gap in the app. On a slow/failed DELETE the row appears frozen or fails silently.
- *Fix:* Mirror the patch pattern — optimistically drop the row in `onMutate`, restore on error, surface a failure. Reset the sticky `confirmingDelete` on scroll/blur or after a timeout so "Sure?" never strands a distracted user into an accidental delete.

**[P1] Server field errors are concatenated machine strings, displaced from their inputs** — `impeccable clarify`
- *Why:* `err.fields.map(f => \`${f.field}: ${f.message}\`).join('; ')` (SubscriptionForm.tsx:80) dumps `date_to: must be after date_from` into one Summary Banner. Contradicts the legibility commitment; the user can't tell which field is wrong.
- *Fix:* Map `f.field` (snake_case) back onto `FormErrors`, route to the offending step (you already have `firstInvalidStep`), show the message inline on the input in human words.

**[P2] Wizard progress is unlabeled; no orientation** — `impeccable onboard`
- *Why:* `<Steps count={5} progress={stepIndex} />` (:144) with no name or "Step N of 5" forces recall (cognitive checklist #3/#5); a distracted mobile user loses their place after an interrupt.
- *Fix:* Add a per-step header ("Where you fly from · Step 1 of 5"); consider making completed dots tappable for backward jumps.

**[P2] Settings is unexplained instrument jargon** — `impeccable clarify`
- *Why:* "Stable-price band (%)", "Cooldown between alerts (hours)", "Price drop worth alerting (%)", and "Signed in as chat {chat_id}" (SettingsScreen.tsx) have labels but no explanation. This is the least-legible screen and hides the anti-spam story (Principle 3).
- *Fix:* Per-field `footer` help; replace "chat {chat_id}" with the Telegram username/first name or drop it.

**[P3] No accelerator for repeat routes; the wizard is the only path** — `impeccable shape`
- *Why:* Every watch = 5 linear steps + 2 checkboxes. The literal target user is "a friend who flies a few known routes." Re-walking the wizard each time fights the "set a watch in under a minute" goal (Heuristic 7).
- *Fix:* A "Duplicate" action on each row that seeds the form, and/or a compact single-screen "quick watch" (origin → destination → price) when alternatives/round-trip aren't needed.

## Persona Red Flags

**Casey (distracted mobile) — most exposed.** Unlabeled `Steps` = no way to see where they were after an interrupt. Sticky `confirmingDelete` (:128–136) never times out: tap Delete → "Sure?", get distracted, return, tap again believing it's the first tap → irreversible delete, no undo. Silent delete (no spinner) invites double-submit against a stale row.

**Jordan (first-timer).** Empty state promises "the warden starts watching" but never shows what an alert looks like — no mental model of the payoff. Settings is a wall of unexplained percentages. The alert step offers two strategies with guidance appearing only *after* you've already chosen `historical_minimum`.

**Sam (a11y).** Status conveyed by badge color (:102) but text label rescues it (near-miss). PriceStepper ±buttons have aria-labels but don't announce the resulting value. The airport suggestion list is plain `Cell`s with no combobox/listbox ARIA, no `aria-activedescendant`, focus stuck in the input — screen-reader users won't perceive suggestions. Raw `chat_id` read aloud is noise.

**Friend-of-owner (project persona, known routes, <1 min).** 5 steps is 3–4 too many for BEG→BCN €150. No saved routes, no duplicate. The create flow is tuned for a stranger configuring everything, not the product's actual audience.

## Minor Observations

- Unsynced magic bottom-paddings (App.tsx:24 = 84; SubscriptionForm.tsx:140 = 96) guard fixed bars — one Tabbar height change and content clips. Tokenize.
- The "Air Tickets Warden" name never appears in the UI it governs.
- `formatDateRange` always appends only the end year; "28 Dec – 3 Jan 2031" hides that departure is in 2030.
- Airport picker has no "No matches" state — empty result and not-yet-typed look identical (both render nothing).
- `withAlternatives`/`withExtraDestinations` are local state not derived from values — correct on load but a little fragile.

## Questions to Consider

1. If the brand is "instrument, not companion," why does no number in the app — price, route, IATA, date — use tabular/monospaced type? What would fares feel like set like a terminal instead of a chat bubble?
2. The Summary is the emotional peak, yet shows only what the user typed. What if it also showed what the watch will *do* — "You'll get a Telegram message when a BEG→BCN fare drops below €150. Wizz Air isn't covered." — turning confirm into the honest-coverage promise (Principle 4)?
3. For the friend who flies three known routes, is a wizard the right shape at all — or is the correct primitive a *saved route* you attach an alert to in one tap?
4. If "anti-spam is a feature," why is it the least-designed screen, buried behind unexplained percentages?
5. `historical_minimum` needs no threshold and is the differentiator ("never force the user to name a number they cannot know") — so why is `absolute_threshold` the default, steering every user toward the number-guessing path the positioning rejects?
